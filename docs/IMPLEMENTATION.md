# 구현 현황과 코드 점검

2026-09-17 갱신. PRD와 Architecture는 전체 게임의 목표 설계이며, 로컬 기록(GM-06)은 아직 후속 범위다.

## 스윙 역동성: 줄 구속·카메라 연출·지면 근접 보너스(2026-09-17)

"정적이다"는 지적에서 출발했다. 진단 결과 원인은 세 가지였다. 부착이 진자가 아니라 전방 추진이라 호가 없었고(반복 스윙 시뮬레이션에서 후반 고도 진폭 6m·속도 30~32m/s로 거의 평탄했다), 카메라가 시야각 90° 고정·수평 고정이라 속도가 화면에 남지 않았으며, 속도 단서가 HUD 숫자뿐이었다.

- **줄 구속(진자).** `physics.ts`에 부착 순간의 거리를 줄 길이로 잡고 내려가는 동안에만 감는(그네 구르기) 구속을 넣었다. 줄보다 멀어지려는 속도 성분을 잘라 내면 남는 접선 속도가 호를 만든다. 좌우(X)는 구속에서 뺐다 — 앵커가 도로 양옆 벽면에 있어 3차원 그대로 당기면 줄이 플레이어를 벽으로 끌고 가 벽에 붙어 멈추는 것을 실제 플레이에서 확인했다. 좌우는 부착 중 감쇠·중앙 복귀가 맡는다.
- **줄이 지키는 한계.** 진자는 전진 속도를 높이로 바꾸므로(에너지 보존) 그대로 두면 정점에서 전진이 음수가 되어 앵커를 감고 돌았다. 전진 하한(16m/s)과 상승 상한(16m/s)을 줄에 걸었다. 되돌림 가속을 60→20m/s²로 낮췄다. 이 상한들이 없을 때 고도 176m까지 솟는 것을 측정했다.
- **보조 재조정.** 세로 당김을 48→32m/s²로 낮추고 고도 52m부터 22m 구간에서 0이 되게 했다(계속 붙잡는 사람이 건물 위로 솟지 않게). 앵커를 지난 뒤에도 전진 성분만 1.2초 남겨(`assistTailSec`) 진자가 뒤로 되말리지 않게 했다.
- **자동 해제.** 앵커 높이까지 솟거나 줄이 사거리(70m)를 넘으면 줄이 풀린다. 놓지 않고 계속 붙잡으면 뒤로 넘어간 앵커가 잡아당겨 전진 속도가 16m/s에 고정되고 줄이 349m까지 늘어나는 것을 실제 플레이에서 확인했다. 재발사는 기존 규칙대로 손을 뗐다 다시 눌러야 하며(사용자 결정), 저절로 풀렸는데 손이 그대로면 HUD에 "손을 떼고 다시 누르세요"를 띄운다.
- **카메라 연출.** `client/host/cameraFeel.ts`를 추가했다. 속도에 따라 시야각 90→106°, 줄이 걸린 쪽으로 최대 14° 기울기, 속도·지면 근접·부착 순간의 흔들림을 준다. 바라보는 방향은 도로 전방(-Z) 고정이다 — 조준은 폰이 하므로 시선까지 돌리면 조준점이 화면 밖으로 밀려난다. 강도는 중간으로 맞췄고 토글은 두지 않았다(사용자 결정).
- **속도선·지면 경고.** 카메라를 스쳐 지나가는 3D 속도선(90개, 속도에 비례해 진해지고 길어짐)과 지면에 가까울수록 진해지는 화면 가장자리 붉은 경고를 넣었다.
- **지면 근접 보너스.** 12m 아래를 18m/s 이상으로 지나는 동안 낮을수록 큰 보너스가 쌓이고 HUD에 "아슬아슬 +N"으로 보인다. 위험을 감수할 이유를 만들기 위한 것이다.
- **검증(자동).** 타입 검사·포맷 검사 통과, 단위 테스트 17파일 145개 통과(줄 구속·상한·카메라 연출·근접 보너스 테스트를 새로 넣고, 옛 보조 모델을 전제하던 물리 테스트 3개를 다시 썼다). 빌드 통과.
- **검증(실제 플레이).** 로컬 Chromium 1440×900, 마우스 입력에서 리듬대로 조작(줄이 풀리면 뗐다 다시 누르기)해 **30초 생존·전진 437m·부착 5회, 고도 2~71m, 속도 16~35m/s, 시야각 91~102°**를 측정했다. 같은 실행에서 `pageerror`·콘솔 오류는 없었다. 저고도 통과 장면에서 속도선·붉은 경고·"아슬아슬" 표시가 함께 나오는 것을 캡처로 확인했다. 변경 전 같은 조작의 측정값은 고도 진폭 6m·속도 30~32m/s였다.
- **확인 안 함.** 실기기 폰 조준으로의 체감, 부스 PC의 프레임률, 처음 잡는 사람이 "뗐다 다시 누르기" 리듬을 얼마나 빨리 익히는지, 카메라 흔들림의 멀미 여부. 모두 실제 사람으로 확인해야 한다.
- E2E는 바뀐 모델에 맞춰 손봤다. 부착 구간이 짧아져 바깥에서 폴링하면 놓치므로 프레임 단위 관찰(`startAttachWatch`, 폰 스윙의 `startSwingRecording`)로 바꿨고, 모달 개편 때 사라진 `#btn-stop`을 누르던 폰 테스트를 `Esc`로 고쳤다(이 변경 전부터 실패하던 테스트다).

## 진단 정보·부착음·바람 소리 제거(2026-09-16)

- 조작 모달의 `진단 정보` 접기(`#diagnostics-section`)와 그 안의 연결·센서·터치·단계·물리·조준각·표적·거미줄·부착·빈도 표시를 모두 없앴다. 표시만 하던 `client/host/diagnostics.ts`(`RateCounter`)와 발사 실패 문구, 화면에 쓰이지 않게 된 `previewTarget`도 함께 지웠다. 화면 위 발사 상태(`#hud-web-status`)와 HUD 점수·속도·정체 경고는 그대로다.
- 이 표시만을 위해 존재하던 `controller:status`의 `sensorHz`·`sendHz`와 컨트롤러의 전송·센서 카운터, `SensorTracker.start`의 이벤트 콜백을 없앴다. 상태 메시지는 `sensorAvailable`·`pageVisible`만 남아 ARCHITECTURE 6절의 계약과 같아졌다. Rapier 초기화 실패는 화면 표시 없이 `console.error`로만 남는다.
- 효과음에서 부착음(`playAttach`)과 속도 기반 바람 소리(`startWind`·`updateWind`)를 없앴다. 발사·빗나감·해제음과 음소거 버튼은 유지한다. 지속음이 사라져 `SfxPlayer`의 바람 노드·음소거 복구 경로도 함께 지웠다.
- E2E가 진단 DOM을 상태 관찰에 쓰고 있었으므로, `tests/e2e/hostProbe.ts`를 새로 만들어 `effects.spec.ts`가 쓰던 방식(테스트 응답에만 관찰 함수를 덧붙이는 `page.route`)으로 4개 파일을 모두 옮겼다. 제품 코드에는 테스트 훅을 두지 않는다. 부착 보조 구간은 짧아 관찰 왕복이 늘면 표본이 종료 뒤로 밀리므로, 폰 스윙 테스트는 한 번 읽은 상태로 여러 검사를 한다.
- 바람 소리를 전제하던 E2E 1개(음소거 해제 시 바람 재생 구분)는 지웠고, 폰 교체 테스트는 임시 효과 정리만 검사한다. 단위 테스트의 바람 관련 2개는 음소거 동작 1개로 바꿨다.
- 검증: 타입 검사·포맷 검사 통과, 단위 테스트 16파일 135개 통과. E2E는 순차 실행에서 18개 중 16개 통과했다. 실패한 `폰 입력: 중지 후 재개…`는 이 변경 전(HEAD)에서도 같은 이유로 실패한다(모달 개편 때 사라진 `#btn-stop`을 누른다). 나머지 1개는 실행마다 다른 테스트가 걸리며(오프라인 재접속 대기, 마우스 부착 후 종료 대기) 단독 재실행에서는 모두 통과했다. 실기기 폰·부스 PC는 미검증이다.

## 전체 화면 캔버스와 조작 모달(2026-09-16)

- 우측 320px 운영자 패널을 없애고 `#game-area`가 화면 전체를 채운다. 패널에 있던 QR·안내·버튼·진단 정보는 `#modal-backdrop` 안의 조작 모달로 옮겼다. 모달은 `playing`에서만 숨고 나머지 단계(`pairing`·`calibrating`·`ready`·`paused`·`gameOver`)에서 화면 중앙에 뜬다. QR은 `pairing`에서만 보인다.
- 플레이 중에는 버튼이 없으므로 `정지` 버튼을 없애고 `Esc` 키로 대체했다(`window`의 `keydown`, 동작은 기존 `operator` 정지와 같다). 소리 끄기·폰 교체는 모달 안에만 있어 플레이 중에는 먼저 `Esc`로 멈춰야 한다.
- `scene.ts`는 그대로 `#game-area` 크기를 기준으로 캔버스·종횡비를 계산하므로 전체 화면에서도 변경 없이 동작한다.
- 검증: Windows 로컬 Playwright Chromium(1440×900, 마우스 입력)에서 대기·플레이·정지 화면을 캡처해 캔버스가 1440×900로 화면을 채우고 플레이 중 모달이 숨는 것, `Esc` 정지와 폰 모드 QR 모달을 확인했다. 타입 검사·포맷 검사·단위 테스트 142개 통과. E2E는 변경 전후 모두 같은 7개가 실패하는 상태라(이 환경의 기존 불안정), 이번 변경으로 추가된 실패는 없다.
- 기존 E2E에서 플레이 중 `#btn-stop`을 누르던 부분은 `Esc`로 바꿨고, 플레이 중 `#btn-mute`·`#btn-switch-phone` 클릭은 숨겨진 버튼을 직접 호출하도록 바꿨다(오디오·세션 동작만 보는 검증이다).

## 현대적 오피스 3종과 게임별 무작위 배치(2026-09-16)

- 일반 파스텔 상자 건물을 블루 커튼월·실버 수직 프레임·그래파이트 벨트 타워 3종으로 모두 교체했다. 제공 사진의 유리 입면을 참고한 창작 모델이며 텍스처는 코드로 생성한다. `/models/?model=offices`에서 같은 모델 3종을 비교할 수 있다. 기존 랜드마크는 유지한다.
- 각 오피스는 로비·프레임·유리·상단 테두리를 재질별 4개 메시로 합치고, 구간 간 geometry·material·texture를 공유한다. 게임의 기존 상자 외곽과 크기를 맞춰 충돌·거미줄 표면을 유지한다.
- 새 게임·재시작마다 새 seed로 건물 높이·간격·모델, 랜드마크 종류·좌우를 결정한다. 랜드마크 등장 간격은 기존 4구간을 유지한다. 같은 게임에서 재개하거나 회수한 구간으로 돌아가면 원래 배치가 재현된다. 아래의 랜드마크 고정 순서와 고정 seed 배치 기록은 이 변경 이전의 이력이다.
- 검증: Windows 로컬 Playwright Chromium(1440×1000, 마우스 입력)에서 3종 미리보기·회전, 실제 게임 외관·부착·정지·재개·추락·재시작을 조작하고 캡처했다. 해당 실행의 `pageerror`는 없었다. 타입 검사·빌드·포맷 검사·단위 테스트 142개 통과. 일반 건물 전체의 모델 대체·충돌체 외곽 일치·모델 자원 재사용, seed별 변화·구간 재현·재시작 변화를 테스트한다.
- E2E 19개는 순차 실행과 폰 테스트 재실행을 합쳐 모두 통과했다. 한 번의 전체 실행에서 모두 통과한 것은 아니다. 첫 병렬 실행은 14/19, 순차 실행은 17/19였으며 순차 실행 중 설정 저장으로 서버가 재시작해 폰 테스트 2개가 중단됐다. 폰 테스트 재실행에서는 대기 화면에 남은 진단 문구를 현재 상태로 검사하던 기존 문제를 발견해 실제 내부 상태를 검사하도록 수정했고, 최종 폰 테스트 3/3이 통과했다. 실제 폰 장착·장시간 성능·부스 PC의 FPS는 미검증이다.

## 네이버 사옥 모델과 게임 배치(2026-09-16)

- 제공 사진을 바탕으로 녹색 유리 격자, 수직 차양, 흰색 NAVER 로고와 저층 출입구를 Three.js 모델로 추가했다. 치수·옥상·가려진 면은 추정이며 실측 복원은 아니다. `/models/?model=naver`에서 전체·정면·외벽 확대와 회전을 볼 수 있다.
- 게임과 미리보기가 `client/host/models/naver.ts`를 공유한다. 기존 애지헌 → 대양AI센터 → 광개토관 다음으로 네이버 사옥이 등장한다. 첫 배치는 구간 14(840~900m), 이후 16구간마다 반복한다. 건물 몸체의 상자 충돌체를 추가해 거미줄 부착과 구간 회수를 연결했다. 창살·캐노피 등 작은 장식은 충돌체에서 생략한다.
- Windows 로컬 Playwright Chromium(1440×1000)에서 모델의 세 시점과 자동 회전 버튼을 확인하고, 실제 게임의 `buildChunk`·`createChunkMeshes`로 구간 13~15를 별도 장면에 렌더링해 배치를 확인했다. 해당 브라우저 실행의 `pageerror`는 없었다. 타입 검사·빌드·단위 테스트 140개·기존 마우스 E2E 5개가 통과했다. 네이버 외벽의 raycast 부착 판정과 구간 회수는 실제 Rapier를 사용하는 단위 테스트로 확인했다. 폰 실기기, 사옥까지의 연속 수동 플레이와 장시간 성능은 미검증이다.

## 거미줄 부착 표현과 인도 확장(2026-09-16)

- 거미줄과 부착 자국을 조금 밝게 조정했다. 부착 자국은 화면을 향하던 방식에서 실제 충돌 표면의 법선에 맞춰 벽에 밀착하는 방식으로 바꾸고, 방사실 길이와 간격을 불규칙하게 조정했다.
- 차도 폭 24m는 유지하고 일반 건물과 랜드마크를 양쪽으로 4m씩 물렸다. 기존 보도블록 바닥이 건물 앞 인도로 드러나며 건물 사이 폭은 32m다. 인도 폭은 시각 조정값으로, 실기기 체감으로 확정한 값은 아니다. 보도는 기존처럼 시각 요소이며 추락 판정은 유지한다.
- Windows 로컬 Playwright Chromium(1440×900, 마우스 입력) 화면에서 인도와 거미줄 부착을 확인했고 `pageerror`는 없었다. 타입 검사·빌드·단위 테스트 139개·마우스 E2E 5개가 통과했다. 실제 폰·부스 모니터·장시간 성능은 미검증이다.

## 거미줄 두께·굴곡·입체감 조정(2026-09-16)

- 참고 이미지 3장 기반의 시안을 `/models/?model=web`에 추가했다. 여러 중심 섬유·느슨한 감김·방사형 접착망을 3D 메시로 만들었다. 전체·길이 방향·섬유 확대와 회전 조작을 제공한다. 사용자 확인 후 접착망 퍼짐 계수를 20% 줄인 모델을 실제 게임에도 적용했다.
- 게임과 미리보기는 `models/webSilk.ts`의 동일한 모델을 사용한다. 게임은 생성한 메시의 정점·법선을 비행·처짐 경로에 맞춰 갱신하며, 프레임마다 지오메트리를 재생성하지 않는다. 접착망은 부착 중에만 표시하고, 비행·빗나감 중에는 숨긴다. 이전 단일 튜브의 지그재그·단면 분할 설정은 제거했다.
- Windows 로컬 Playwright Chromium(1440×900, 마우스 입력)에서 미리보기 세 시점과 게임 부착 화면을 캡처해 확인했고 `pageerror`는 없었다. 단위 테스트 136개 통과. 실제 폰·부스 모니터·장시간 성능은 미검증이다.
- 최종 타입 검사·빌드 통과. E2E 19개는 모두 통과한 실행을 확인했으나, 전체 실행 한 번에 전부 통과하지는 않았다. 병렬 실행은 음소거 재클릭 전에 종료되는 테스트가 실패(18/19), 순차 실행은 그 테스트가 통과하고 오프라인 재접속 대기가 실패(18/19)했다. 재접속 테스트는 단독 재실행에서 통과했다. 거미줄·마우스·모의 폰 플레이 테스트는 두 전체 실행에서 통과했다.

아래는 섬유 모델 적용 전 단일 튜브 조정 기록이다.

- 납작한 띠와 어두운 외곽선을 제거하고, 8분할 원형 단면과 `MeshStandardMaterial`로 장면 조명을 받는 튜브를 만든다. 발사 줄과 부착 줄에 함께 적용한다.
- 거리 대비 반지름을 0.006 → 0.0025, 굴곡 폭을 0.018 → 0.003, 굴곡 횟수를 3 → 1.5로 줄였다. 경로 분할은 24 → 48로 늘려 곡선을 부드럽게 한다. 시각 조정값이며 실기기 측정으로 확정한 값은 아니다.
- Windows 로컬 환경에서 타입 검사·단위 테스트 136개·빌드 통과. 단면 법선과 삼각형의 바깥 방향이 일치하는 것도 검사했다. 실기기와 부스 모니터에서의 가독성·체감은 미검증이다.
- 로컬 Playwright Chromium(1440×900, 마우스 입력)에서 발사·부착 후 화면을 캡처해 가는 줄, 완만한 굴곡, 외곽선 제거와 표면 음영을 확인했다. 해당 실행의 `pageerror`는 없었다.

## 만화풍 거미줄과 포물선 비행(2026-09-16)

직선으로 뻗으며 밝기가 깜빡이던 발사선을, 중력을 받아 완만하게 휘는 비행과 만화풍 거미줄 가닥으로 바꿨다.

### 바꾼 것

- **포물선 비행과 구간 충돌 검사.** 줄 끝이 `web.travelGravity`(20m/s²)로 처지는 탄도를 그린다. 매 물리 step마다 직전 줄 끝에서 현재 줄 끝까지의 구간만 raycast(+조준 보정 스윕)해 처음 걸리는 벽면에 부착한다. 최대 사거리는 날아간 경로 길이로 잰다. `selectTarget`은 발사 전 표적 미리보기에만 남는다.
- **만화풍 가닥(`createWebStrand`/`updateWebStrand`).** 선(`THREE.Line`) 두 개를 카메라를 향한 띠 메시로 바꿨다. 흰 심 + 굵은 어두운 외곽선(심을 카메라 쪽으로 5cm 당겨 겹침 깜빡임 방지) + 날아가는 동안의 끝 뭉치. 발사 중 줄과 부착 줄이 같은 모양을 쓰고, 부착 줄은 가운데가 최대 1.2m 늘어진다.
- **모든 크기를 시선 기준으로.** 굵기·지그재그 폭은 카메라까지 거리에 비례(화면에서 일정), 가닥 샘플 간격은 두 점을 바라보는 시선 각도 기준이다. 월드 길이로 샘플하면 줄이 카메라 위치에서 출발하는 탓에 점 대부분이 화면 한곳에 몰려 지그재그가 끝부분에만 뭉쳤다(정점을 화면 좌표로 찍어 확인했다).
- **점멸 제거.** `effects.firePulsePerMs`를 없애고 발사 중 불투명도를 1로 고정했다. 빗나간 줄만 사라지며 흐려진다.

### 확인한 것 / 못 한 것

- 확인함: 브라우저(마우스 모드)에서 발사 → 곡선 비행 → 벽면 부착 → 보조 상승(vel y −2.6 → +1.4)을 실제로 관찰하고 화면도 캡처했다. `npx tsc --noEmit` 통과, 단위 테스트 136개 통과, e2e 19개 중 18~19개 통과(아래 참고).
- 확인 못 함: 실기기 체감. 중력 20m/s², 굵기 0.6%·지그재그 1.8%(거리 대비)가 적절한지는 부스 환경에서 보지 않았다. 폰 화면 크기에서의 가독성도 확인하지 않았다.
- e2e는 전체를 한 번에 돌리면 간헐적으로 하나씩 실패한다(빗나감 재시도 테스트, 오프라인 감지 테스트). 각각 단독으로는 통과한다. 빗나간 발사가 최대 사거리까지 날아가는 0.6초가 더해져 한 판(낙하까지 약 1.9초) 안에 담기는 동작이 빠듯해진 것이 한 원인이라, 재시도 검증은 새 판에서 하도록 고쳤다.

## 거미줄 연장 발사(2026-09-16)

누른 순간 줄이 빛처럼 즉발되어 부착되던 것을, 누르는 동안 줄 끝이 뻗어나가다 건물에 닿는 순간 부착하도록 바꿨다. 물리 보조(전방 추진·당김)는 부착 시점부터 시작하므로, 먼 곳에 걸수록 반응이 늦게 온다.

### 바꾼 것

- **발사 순간 표적 확정 제거.** `WebSwing`의 `firing` 단계가 발사 순간 고정한 출발점·방향(`fireOrigin`/`fireDirection`)을 따라 `reach = 경과시간 × travelSpeedMps`만큼 뻗은 길이를 유지하고, 매 업데이트마다 `maxDistance = reach`로 `selectTarget`을 호출한다. 아직 줄 끝이 닿지 않은 건물은 걸리지 않는다. 기존 조준 보정(직접 raycast → 반경 2.5m 구체 스윕)과 가림·최소 사거리 판정은 그대로 쓴다.
- **`web.fireEffectSec`(0.1초) → `web.travelSpeedMps`(120).** 최대 사거리 70m까지 약 0.58초다. 체감 검증 전 제안 초기값이며 실기기로 재지 않았다.
- **실패 사유 정리.** 발사 후 재검사가 사라져 `outOfRange`/`occluded`가 발생할 수 없으므로 `FireFailure`를 `noTarget`/`releasedWhileFiring`만 남겼다.
- **콜백 변경.** `onFireStart`는 표적 없이 호출되고(발사 시점에 표적이 없다), `onFireMiss(tip, direction)`는 최대 사거리에 도달한 줄 끝과 방향을 넘긴다. `pendingTargetPoint` → `tipPoint`(현재 줄 끝)로 바꿔 발사선이 뻗어나가는 것을 그대로 그린다.
- **빗나감 연출.** 걸리지 못한 줄은 발사와 같은 속도로 같은 방향을 계속 날아가며 `effects.missBeamDurationMs`(260ms) 동안 흐려진다.

### 확인한 것 / 못 한 것

- 확인함: `npx tsc --noEmit` 통과, 단위 테스트 134개 통과(`web.test.ts`는 줄 끝 진행·닿기 전 미부착·발사 방향 고정·빗나감 콜백을 새로 검증한다).
- 확인 못 함: 실기기·브라우저에서의 체감. 120m/s가 적절한지, 부착 지연이 스윙 리듬을 해치지 않는지는 플레이로 확인하지 않았다.

## 세종대 랜드마크 배치와 확대(2026-09-16)

애지헌에 이어 대양AI센터도 무한 도로에 배치하고, 둘 다 기존보다 크게 놓았다.

### 바꾼 것

- **두 랜드마크 교대 배치.** `buildChunk`가 `landmarkFirstChunk`(2)부터 `landmarkEveryChunks`(4) 간격으로 랜드마크를 놓고 애지헌·대양AI센터를 번갈아 고른다. 한 쌍마다 좌우를 바꿔 두 종류 모두 양쪽에서 보인다. 구간 index로만 정해지므로 재시작·재생성 시 같은 배치다.
- **종류별 충돌체.** `landmarkColliders`가 종류에 따라 애지헌 12개·대양AI센터 6개의 상자를 배치 좌표로 옮긴다. 물리 등록은 `chunkBuildingColliders(chunk)`로 일반 건물과 함께 넘긴다.
- **종류별 확대 배율.** `world.landmarkScale`을 단일 숫자에서 `{ aejiheon: 1.6, 'daeyang-ai': 1.25 }`로 바꿨다. 애지헌은 55.1m → 88.2m, 탑 몸통 폭 8m → 12.8m가 돼 일반 건물(45~70m)보다 확실히 크다. 대양AI센터는 54.9m → 68.6m, 바닥 48×42m → 60×52.5m다.
- **대양AI센터 배율이 1.25로 묶인 이유.** 바닥 폭 48m × 배율이 구간 길이 60m를 넘으면 랜드마크가 이웃 구간까지 넘어가 구간 단위 생성·회수와 어긋난다. 60/48 = 1.25가 상한이라 더 키우려면 `chunkLengthM`부터 바꿔야 한다. 애지헌은 바닥 폭이 20.1m라 여유가 있다.
- **바꾸지 않은 것:** 물리·조준·입력·네트워크 메시지, 일반 건물 생성 규칙, 구간 스트리밍 규칙. 새 패키지도 없다.

### 확인한 것 (Windows 로컬, Node.js v24.19.0, 실제 Rapier, Playwright 기본 Chromium)

- 타입 검사, 단위 테스트 16개 파일 136개, E2E 19개, 빌드 통과. 빌드에는 기존 500kB 초과 청크 경고가 남는다.

## 전진 가속·상승력 강화(2026-09-16)

## 도로 전방 중심의 거미줄 이동(2026-09-15)

부착점 중심의 고정 길이 진자를 없애고, 부착 중에만 걸리는 **전진 보조 + 부착점 방향 당김**으로 바꿨다.

### 바꾼 것

- **줄 구속 제거.** 양방향 길이 구속, 부착 직후 0.6m 감기, 길이 오차 보정 속도를 모두 지웠다. 부착점은 실제로 맞은 지점 그대로 저장하고 줄 길이는 저장하지 않는다. 화면의 줄은 플레이어에서 부착점까지 실제 거리라 이동에 따라 길이가 변한다. `attach()`는 길이 인자가 사라져 `attach(point)`가 됐다.
- **매 step 보조.** 적분 직전에 가속도 × dt를 속도에 더한다. 전방은 전진 속도가 `assistForwardTargetSpeed`(18m/s)보다 느릴 때만 `assistForwardAccel`(8m/s²)로 목표까지만 채우고, 이미 빠르면 건드리지 않는다. 좌우·상하는 플레이어에서 부착점으로 향하는 단위 벡터의 X·Y 성분에 `assistLateralAccel`(4m/s²)·`assistVerticalAccel`(24m/s²)을 곱해 더한다. 거리로 세기를 바꾸지 않는다.
- **보조 종료 조건.** 부착점까지 남은 전방 거리가 `assistFadeDistanceM`(5m) 이내면 모든 보조를 선형으로 줄이고, 부착점의 Z에 도달하면 그 부착의 보조를 끝낸다. 뒤로 밀려도 다시 켜지지 않는다. 계속 나아가려면 앞쪽에 다시 쏴야 한다. 보조가 끝나도 줄은 손을 뗄 때까지 그대로 보이고 자동 해제·재발사는 없다.
- **부착 순간 1회 접선 추진(`forwardSwingBoost`) 제거.** 매 step 보조와 중복이라 함수와 설정을 함께 지웠다.
- **진단 표시.** 앵커 정보가 `줄 길이/앵커 거리`에서 `앵커까지 실제 거리 / 보조 중·종료`로 바뀌었다. e2e 관찰 훅의 타입도 같이 고쳤다.
- **바꾸지 않은 것:** 입력(누름 1회 = 발사 1회), 표적 선택·조준 보정, 앵커 높이 제한 없음, 해제 시 속도 보존, 센서·네트워크 메시지 계약.

### 상하 당김 계수를 24로 올린 이유(측정)

계획의 제안 초기값 14로 구현해 실제 월드에서 측정하니, 위를 겨눠도 계속 가라앉아 곧 추락했다. 당김의 위 성분이 `24 × (높이차 / 부착 거리)`라 먼 부착점(거리 32m·높이차 16m)에서는 7m/s²뿐이라 중력 9.81m/s²을 이기지 못한다. 시작 `[0,18,0]`·초기 속도 14m/s·조준 우 30°/상 30° 고정으로 측정한 생존 시간이다.

| 상하 당김 | 계속 누름 | 0.6초마다 재발사 |
|---|---|---|
| 14 | 2.95초 | 3.27초 |
| 18 | 3.35초 | 4.48초 |
| 24 | 4.02초 | 6.08초 |
| 30 | 4.68초 | 8.07초 |

24를 골랐다. 30은 더 오래 버티지만 가까운 부착점에서 당김이 세지고 측정에서 x가 벽면(±12m)에 더 붙었다. **이 값들은 자동 테스트 측정이며 실기기 체감 검증은 하지 않았다.**

### 확인한 것 (Windows 로컬, Node.js v24.19.0, Playwright 기본 Chromium)

- 타입 검사, 단위 테스트 15개 파일 131개, E2E 19개, 빌드 통과.
- 부착 보조 단위 테스트를 새로 썼다: 10초 뒤 전진 속도가 목표 18m/s에 수렴, 목표보다 빠른 25m/s로 시작하면 10스텝 동안 z속도가 그대로, 좌우 당김이 ±대칭, 높은 부착점은 위·낮은 부착점은 아래로 당김, 부착점 앞 2.5m에서 전방 보조가 정확히 절반, 부착점 통과 후 `assisting`이 꺼지고 위치를 뒤로 되돌려도 다시 켜지지 않음, 해제 후 30스텝이 동일 조건 비부착 플레이어와 일치, 부착이 자유낙하보다 5m 높고 1m 이상 더 전진, 당김 경로의 벽을 관통하지 않음.
- 실제 월드(폰 조준 → 표적 선택 → 부착)에서 보조를 받는 동안 전방으로 10m 이상 나아가고 전진 속도가 목표를 넘지 않으며 고도를 5m 넘게 잃지 않는다.

### 확인하지 못한 것

- **실기기 체감.** 위 값(18·8·4·24·5m)은 모두 측정 전 초기값이거나 자동 테스트로만 고른 값이다. 폰·손목 장착 플레이로 확인하지 않았다.
- **연속 플레이 길이.** 고정 조준 기준 생존 4~6초다. 실제로는 앞쪽 표적을 계속 바꿔 쏘는 것을 전제로 하며, 사람이 그렇게 칠 수 있는지는 확인하지 않았다.
- **좌우 당김의 벽 접근.** 부착점이 건물 벽면(±12m)이라 당김이 플레이어를 벽 쪽으로 끌고 간다. 측정에서 x가 10m를 넘었다. 도로 이탈·충돌 빈도는 실기기 확인 후 판단한다.
- **정체 종료와의 관계.** `progress`의 5m/8초는 건드리지 않았다.

## 짧은 당김 후속 점검(2026-09-15)

- 추가 점검에서 당김 계산의 런타임 오류는 재현되지 않았다. 줄을 먼저 줄인 뒤 거리 오차를 속도로 환산하므로 감기 속도가 이미 포함된다. 별도 감기 속도를 더해 당김을 중복 적용하지 않도록 해당 코드 주석을 보완했다. 물리 계산과 튜닝값은 변경하지 않았다.
- 당김 완료 스텝 수를 계산하는 테스트의 `Math.round`를 `Math.ceil`로 수정했다. 튜닝 후 필요한 스텝 수가 정수가 아니어도 완료 전에 검사하지 않도록 한다.
- 실제 Rapier 월드 테스트를 추가했다. 당김 3스텝 후 해제한 플레이어를 동일 위치·속도의 비부착 플레이어와 30스텝 비교해 자유비행을 확인했다. 당김 경로의 벽 충돌에서 플레이어 반경을 고려한 벽면 침투가 0.02m 허용 오차 이내인지, 해제 후 반대 방향 속도를 주면 벽에서 벗어나는지도 확인했다.
- 거리 3m·70m 경계 표적을 기존 테스트에 추가했다. 첫 스텝에 실제 앵커 거리가 0.04m 이상 줄고, 당김 후 고정 길이 오차가 0.1m 이내인지 검사한다.
- Windows 로컬 환경, Node.js v24.19.0, 실제 Rapier를 사용한 단위 테스트 15개 파일 135개, 로컬 서버·Playwright 기본 Chromium E2E 19개, 타입 검사·빌드·변경 코드 포맷 검사 통과. 빌드에는 기존 대형 번들 경고가 남는다. 실기기 폰·손목 장착·체감과 성능 측정은 수행하지 않았다. 벽 충돌 테스트는 위의 특정 배치에 대한 자동 검증이며 모든 충돌 상황을 보장하지 않는다.

## 부착 직후 짧은 당김 추가(2026-09-15)

### 바꾼 것

- **부착 순간 0.6m 당김.** 부착 시 줄의 목표 길이를 부착 거리보다 `attachPullDistanceM`(0.6m) 짧게 잡고, 매 물리 step `attachPullSpeed`(3m/s)로 줄인다. 약 0.2초(12 step) 만에 목표에 닿으면 감기를 끝내고 기존 고정 길이 진자로 이어간다. 줄 길이 변화가 기존 양방향 속도 구속의 목표 길이에 그대로 들어가므로 별도 힘 계산 없이 첫 step부터 안쪽 속도가 생긴다. 플레이어 위치는 옮기지 않아 Rapier 충돌 처리는 그대로다.
- **시간이 아니라 속도로 정했다.** 2026-09-14 기록의 이유와 같다. "정해진 시간에 걸쳐 부착 거리의 몇 배까지" 감으면 먼 표적일수록 당김이 세져 도로 밖으로 쏘아진다. 거리 0.6m·속도 3m/s로 고정하면 3m 표적과 70m 표적이 같게 당겨진다.
- **유지한 것:** 부착 순간의 전방 접선 보조(`attachSwingBoostSpeed`), 당김은 부착당 한 번(누르고 있어도 반복 없음), 벽면 높이 제한 없음, 해제 시 속도 보존, `attach()` 인터페이스와 네트워크 메시지 계약. 앵커 내부에 목표 길이 필드만 추가했다.

### 확인한 것 (모두 이 저장소에서 실행)

- 타입 검사, 단위 테스트 15개 파일 133개, 브라우저 테스트 19개, 프로덕션 빌드 통과. 빌드에는 기존 대형 번들 경고가 남는다.
- 대표 전방 상향 앵커 (12,30,-23) / 시작 (0,18,0) / 초기 속도 (0,0,-14)에서: 첫 물리 step 직후 반경 방향 속도가 안쪽(음수)이고 크기가 3m/s에서 0.5m/s 이내(중력 한 step 적분분), 12 step 뒤 줄 길이가 정확히 0.6m 짧아진 뒤 그 이상 줄지 않으며, 이후 3초(180 step) 동안 길이 고정·앵커 거리 오차 0.1m 이내다. 기존 전방 이동·하강 후 재상승 궤적도 그대로다.
- 가까운 앵커 (6,22,-6)과 먼 앵커 (10,40,-55) 모두 한 step에 같은 양(3m/s × 1/60초)만 줄고, 감기 후 길이가 부착 거리 -0.6m로 같다.
- 당김 도중(3 step) 해제하면 속도가 그대로 보존되고, 다시 부착하면 남은 감기가 아니라 0.6m 당김이 새로 시작된다.
- 줄 길이(20m)보다 가까운 12m에서 부착해도 2초 뒤 앵커 거리가 19.4m로 되돌아온다(양방향 구속 + 당김).
- 일시정지 중에는 물리 step을 돌리지 않으므로 감기도 멈춘다. 재시작은 기존 경로대로 `detach()`로 앵커를 지워 당김 상태까지 함께 초기화된다. 브라우저 중지·재개·재시작 테스트가 그대로 통과한다.

### 확인하지 않은 것

## 부착 줄 표시·상향각 제한 제거·즉시 진자 스윙(2026-09-15)

### 고친 것

- **부착 줄이 화면에서 한 점으로 겹치던 문제.** 부착 줄의 시작점은 매 프레임 플레이어(=카메라) 위치라 원근 투영에서 두 끝점의 시선이 거의 같은 방향이 되어 선이 점으로 보였다. 발사 연출에서 이미 고쳤던 것과 같은 원인인데 부착 줄에는 적용되어 있지 않았다. `updateRopeLine`이 시작점 오프셋을 직접 적용하도록 옮겨, 발사·빗나감·부착 줄이 같은 경로를 쓴다. 설정 이름도 `effects.fireBeamOriginOffsetM` → `effects.beamOriginOffsetM`으로 바꿨다. 물리 앵커(끝점)는 그대로다.
- **앵커 최소 상향각(20°) 제거.** 직선 ray로 맞힌 점의 상향각은 조준 pitch와 같아, 이 규칙은 실질적으로 "20° 미만으로 겨누면 부착 불가"였다. 낮은 벽면을 겨누면 눌러도 아무것도 걸리지 않아 고장처럼 보인다. 사용자 결정에 따라 제거했다. `web.minAnchorElevationDeg`, `SwingOptions.minElevationDeg`, `isAboveMinElevation`, 실패 사유 `tooLow`와 관련 진단 문구가 함께 사라졌다. 사거리(3~70m)·가림·직접 조준 우선은 유지한다.
- **줄 감기 제거, 부착 즉시 고정 길이 진자로 변경.** 부착 순간의 앵커까지 거리를 그대로 고정 줄 길이로 쓴다. 구속은 "멀어질 때만"에서 **양방향**으로 바꿔, 매 step 적분 직전에 반경 방향 속도를 지우고 길이 오차만 속도로 되돌린다. 접선 속도와 중력만 남으므로 부착 첫 step부터 진자다. 앵커 쪽으로 날아가도 줄이 느슨해지지 않는다. `ropeTargetFactor`·`ropeWinchSpeed`·`ropeMaxPullSpeed`가 사라지고 오차 보정 속도 상한 `ropeCorrectionSpeed`(8m/s) 하나만 남았다. 위치 순간이동은 여전히 하지 않고 Rapier 충돌 처리를 그대로 쓴다.
- **바꾸지 않은 것:** 입력(누름 1회 = 발사 1회, 부착 후 앵커 고정, 마지막 손가락 해제 시 즉시 해제·속도 보존)은 이미 그렇게 동작해 손대지 않았다. 초기 전방 속도와 부착 시 1회 접선 보조도 유지했고 지속 전진력은 넣지 않았다. 네트워크 메시지 계약도 그대로다.

## 거미줄이 이동에 영향을 주지 못하던 문제와 물리 재작업(2026-09-14)

> 이 절은 당시 기록이다. 여기서 도입한 **줄 감기와 앵커 최소 상향각은 2026-09-15에 제거**됐다(위 절 참고). rope joint를 쓰지 않는 직접 속도 구속과 구체 스윕 보정은 그대로 유지된다.

### 확인한 원인 (헤드리스 Rapier 시뮬레이션)

`PhysicsWorld.attach()`가 Rapier **rope joint**를 쓰고 `main.ts`가 줄 길이로 부착 순간 거리를 그대로 넘겼다. rope joint는 **최대** 거리만 제한하는데, 표적은 거의 항상 플레이어 앞쪽에 있고 플레이어는 -Z로 14m/s로 날아가므로 부착 직후 앵커까지 거리가 **줄어들어** 줄이 끝까지 느슨했다. 화면에는 "부착됨"이 뜨고 줄도 그려져 성공한 것처럼 보였다.

시작 `[0,18,0]`, 속도 `[0,0,-14]`, 줄 길이 = 부착 거리로 측정한 결과:

| 앵커 | 거리 | 줄이 팽팽해진 시각 | 결과 |
|---|---|---|---|
| (12,18,-12) | 17.0m | 1.27s | 간신히 |
| (12,18,-23) | 25.9m | 없음(끝까지 느슨) | 1.92s 추락 |
| (12,18,-60) | 61.2m | 없음 | 1.92s 추락 |

부착하지 않아도 1.92s에 추락하므로, **20m 이상 앞을 걸면 궤적이 부착 없음과 동일했다.** 후보점 높이가 `height * 0.6`이고 구간 0의 건물 높이가 30으로 고정이라 후보 y가 정확히 시작 높이(18)와 같았던 것도 겹쳤다 — 위에서 매달리는 게 아니라 수평으로 거는 꼴이었다.

### 고친 것

- **rope joint 제거, 직접 속도 구속.** 앵커는 좌표 데이터일 뿐이고 Rapier joint를 만들지 않는다. 매 step의 적분 직전에 앵커까지 거리가 줄 길이 이상일 때만 줄 방향으로 멀어지는 속도를 지운다. 초과 거리는 위치를 옮기지 않고 속도로 되돌린다(위치를 옮기면 렌더 보간이 튀고 건물을 관통한다).
- **부착 직후 줄 감기.** 부착 거리의 `ropeTargetFactor`배까지 `ropeWinchSpeed`로 감는다. 감는 동안 줄이 거리보다 짧아져 위 구속이 그대로 당기는 힘이 된다. **처음에는 "정해진 시간에 걸쳐 선형으로" 감도록 짰다가 버렸다** — 그러면 줄이는 속도가 부착 거리에 비례해 커지고(40m 부착이면 25m/s), 측정에서 속도가 14→29m/s로 뛰며 플레이어가 도로 밖 x=28까지 쏘아졌다. 시간이 아니라 속도로 정해 해결했다.
- **당김 상한의 위치.** 멀어지는 속도를 지우는 것은 줄의 비신축성 그 자체라 제한하지 않는다. 상한(`ropeMaxPullSpeed`)은 안쪽으로 끌어당기는 속도에만 건다. 처음에는 둘을 합쳐서 클램프했고, 그래서 매 step 8~12m/s가 누적 적용되는 형태가 됐다.
- **부착 후보점 개념 제거, `castShape` 구체 스윕으로 교체.** `world.ts`의 후보 생성, `ChunkedWorld.candidates`, `rebuildCandidates`, `web.ts`의 `findCandidateTarget`이 사라졌다. 벽면 어디든 걸리고 첫 접촉만 돌려주므로 가림이 자동으로 걸러진다. `calibrationSearchHalfAngleDeg`(12°)는 참조가 사라져 삭제하고 `web.aimAssistRadiusM`(2.5m)로 대체했다.
- **`castShape` 결과 좌표계 주의.** rapier3d-compat 0.20에서 건물 쪽 접촉점을 월드 좌표로 주는 것은 **`witness1`**이다(`witness2`는 구체 로컬). 타입 정의 주석은 반대로 적혀 있어 실제 값을 찍어 확인했다. 처음에 `witness2`를 썼다가 접촉점이 벽면에서 벗어났고, 단위 테스트가 잡았다.
- **앵커 최소 상향각(`minAnchorElevationDeg`, 20°).** 수평에 가까운 앵커는 진자가 옆으로만 돌아 플레이어를 벽으로 끌고 가므로 표적에서 제외한다. 실패 사유 `tooLow`를 새로 만들어 진단에서 "표적 없음"과 구분한다. 직선 ray로 맞힌 점의 상향각은 조준 pitch와 같으므로, **실질적으로 20° 미만으로 겨누면 부착이 안 된다. 아래쪽 조준 허용각(35°)은 부착에 쓰이지 않게 됐다.**
- **월드.** 건물 높이 30~50m → 45~70m. 시작 높이 18m 위에 걸 수 있는 벽면을 확보하기 위해서다. 구간 0의 고정 높이·고정 시작 거리 특례는 없앴다.

### 확인한 것

- 타입 검사, 단위 테스트 15개 파일 126개 통과(신규: 감기 목표 도달, 부착이 자유낙하 대비 궤적을 바꿈, 접선 속도 보존, 장시간 초과 거리 누적 없음, `sweepBuilding` 3개, 상향각 관련 5개).

- 전체 e2e를 한 번에 돌리면 `phoneSwing`의 빗나감 테스트가 `calibrating`에 머물러 실패하는 일이 있다. **변경 전 코드(`git stash`)에서도 전체 실행 시 다른 테스트(`effects.spec.ts:88`)가 같은 방식으로 실패했으므로 이번 변경이 만든 것이 아니다.** 개별 실행에서는 모두 통과한다.

### 확인하지 않은 것

- **실기기 폰 플레이와 사람이 느끼는 체감 전부.** 아래 수치는 모두 측정값이 아닌 제안 초기값이다: `ropeTargetFactor 0.75`, `ropeWinchSpeed 8`, `ropeMaxPullSpeed 8`, `aimAssistRadiusM 2.5`, `minAnchorElevationDeg 20`, `buildingHeightRangeM [45,70]`.
- 20° 상향각 하한이 처음 잡는 사람에게 자연스러운지. 조준을 아래에서 위로 훑으면 20°에서 표적 마커가 딱 켜진다(점진적이지 않다).
- **정체(stalled) 종료 빈도.** 줄을 짧게 걸면 스윙 반경이 줄어 한 번에 전진하는 거리가 준다. 측정에서 가까운 앵커(13~16m)는 5초 뒤 출발 지점 근처로 돌아왔다. `progress`의 5m/8초를 미리 건드리지 않았으니 실플레이에서 관찰되면 조정한다.
- **가까운 표적에서 벽으로 끌려가는 문제는 이번 범위에서 제외했다.** 측정에서 앵커가 x=±12 벽면에 있어 진자가 플레이어를 x=11~15까지 끌고 간다. 실기기 확인 후 별도로 판단하기로 했다.

## 최근 구현 재점검과 수정(2026-09-14)

기능을 더하지 않고 최근 구현분(무한 도로·점수·연출·소리·손목 조준·도로 이탈 종료)만 다시 읽고 고쳤다.

- **부착 보조가 정면 표적에서 엉뚱한 방향으로 튀던 문제(고침):** `forwardSwingBoost`가 전방 벡터의 접선 성분을 정규화해서 썼다. 줄이 전방과 나란할수록 접선 성분은 0에 가까워지는데도 항상 최대 속도가 나가, 70m 앞처럼 거의 정면인 표적에 걸면 2m/s가 옆·아래로 붙었다(계산으로 확인: 원점 (0,18,0)·앵커 (12,24,-68)에서 보조 방향 (-0.86, -0.43, -0.29)). 접선 길이를 그대로 곱해 줄이 전방과 수직일 때 최대, 나란할 때 0이 되게 했다. **표적 방향에 따라 실제 보조가 2m/s보다 작아지므로 체감이 달라진다. 값은 여전히 측정값이 아닌 제안 초기값이며 실제 플레이 후 `attachSwingBoostSpeed`를 다시 맞춰야 한다.**
- **부착 플래시의 경과 시간 기준 불일치(고침):** 시작 시각만 `performance.now()`로 잡고 프레임 루프는 `requestAnimationFrame` 시각으로 경과를 계산해, 부착한 그 프레임에서 경과가 음수가 되어 불투명도가 1을 넘을 수 있었다. 빗나감 연출에서 이미 고쳤던 것과 같은 유형이라 같은 기준(물리 호출에 전달한 프레임 시각)으로 통일했다.
- **종료 경로 정리:** 바닥 접촉·도로 이탈·정체 종료가 각각 줄 해제와 상태 전이를 되풀이했다. `endRun`으로 모아 종료 경로가 줄 해제를 빠뜨릴 수 없게 했고, 도로 이탈 판정도 한 번만 계산한다.
- **입력마다 하던 표적 재계산 제거:** 폰 입력 수신 콜백이 `updateCrosshair()`를 다시 불렀지만 조준 방향은 프레임 루프에서만 갱신되므로, 표시는 같은 값이고 표적 탐색 raycast만 입력 빈도(60~120Hz)만큼 더 돌았다. 프레임 루프의 갱신만 남겼다.
- **자잘한 정리:** 매 프레임 새로 만들던 발사 설정 객체를 상수 하나로 공유해 미리보기와 실제 발사가 갈라질 수 없게 했고, 속도 크기 계산을 프레임당 1회로 줄였으며, 읽는 곳이 없던 `sensorRate`를 지웠다.
- **취약 e2e 수정:** `빗나간 발사...` 테스트가 벽시계로 400ms 기다린 뒤 `playing`을 확인해, 실행이 조금만 느려지면 낙하 종료(약 1.9초)가 먼저 와서 실패했다. **수정 전 코드에서도 `--repeat-each=3`으로 3/3 재현했으므로 이번 변경이 만든 실패가 아니다.** 빔이 사라진 순간의 단계를 브라우저 프레임 안에서 기록해 판정하도록 바꿨다. 연출 시간을 100초로 늘리면 실패하는 것으로 이 판정이 살아 있음을 확인했다.
- **확인함:** 타입 검사, 단위 테스트 15개 파일 113개(신규 2개: 접선 크기 감쇠, 전방 정렬 시 보조 없음), 브라우저 테스트 19개, 빌드 통과. 변경한 파일 기준 Prettier 검사 통과. 위 e2e는 8회 반복 실행으로 안정성을 확인했다.
- **확인 안 함:** 실기기 폰 플레이와 사람이 느끼는 부착 보조의 체감. 자동 검증은 방향과 크기 규칙만 고정하며 재미를 보장하지 않는다.
- **고치지 않고 남긴 것:** `client/host/main.ts`(약 710줄)의 상태 전이·HUD·프레임 루프 분리는 이번에도 하지 않았다. 행사(2026-09-17)까지 남은 기간에는 회귀 위험이 더 크다고 봤다. 저장소에 남은 `dev-server.log`·`tunnel.log`는 `.gitignore` 후보이나 이번에 건드리지 않았다.

## 발사 연출 변경분 재점검(2026-09-13)

## 폰 조준 좌우 회전 수정과 빗나감 연출(2026-09-13)

실기기 연결 테스트에서 "거미줄 발사 연출이 보이지 않고 부착도 안 되며 시작하자마자 추락한다"는 보고를 받고 원인을 찾아 고쳤다.

- **원인(재현·확인함):** 폰 조준이 좌우로 전혀 움직이지 않았다. DeviceOrientation 쿼터니언은 기기 좌표를 지면 좌표(Z가 위)로 옮기는 값인데, 기존 `aim.ts`는 그 상대 회전을 게임 좌표계(Y가 위, 전방 −Z)의 전방 벡터 `(0,0,-1)`에 그대로 적용했다. 수직축이 서로 달라 팔을 좌우로 돌리는 회전이 조준에 반영되지 않았다. 손목 평면 장착 자세로 계산해 확인한 값: 팔 오른쪽 30°(alpha −30) → yaw 0.0°, 팔 왼쪽 30° → yaw 0.0°, 손목 위 30°(beta +30) → pitch 30.0°, 손목 롤 30°(gamma +30) → yaw −30.0°. 즉 좌우는 죽고 손목을 비틀어야만 좌우가 움직였다. 건물은 좌우 ±12m라 걸려면 yaw 20~40°가 필요하므로 `selectTarget`이 항상 `null`을 반환했고, `firing` 단계 자체를 거치지 않아 발사선도 보이지 않은 채 추락했다.
- **조준 계산 교체:** `relativeRotation`·`relativeRotationToAngles`를 `aimAnglesFromOrientation`으로 바꿨다. 기기 좌표의 조준축(`DEVICE_AIM_AXIS = [0, 1, 0]`, 폰 상단=손가락 방향 장착 기준)을 지면 좌표로 옮긴 뒤, 보정 자세 `q0`의 조준축과 비교해 수평 방위 차를 yaw, 고도 차를 pitch로 쓴다. 장착 자세가 달라도 팔을 돌린 만큼 좌우가 움직이고, 조준축을 중심으로 한 손목 롤은 조준을 바꾸지 않는다. 벡터 회전은 `shared/quaternionMath.ts`의 `rotateVectorByQuaternion`로 공용화했다(기존 `relativeRotationToAngles` 안에 있던 식을 그대로 옮겼다).
- **빗나감 연출:** 표적을 못 찾은 발사에서 `WebSwing`이 `onFireMiss(aimDirection)`를 한 번 호출한다. `main.ts`는 조준 방향으로 최대 사거리(70m) 지점까지 거미줄을 뻗었다가 260ms 동안 흐려지게 하고(`missBeamDurationMs`), `SfxPlayer.playMiss()`로 낮은 실패음을 낸다. 눌렀는데 화면에 아무 반응이 없던 문제를 없앤다. 상태기계·발사 판정·물리는 바꾸지 않았다.
- **바꾸지 않은 것:** 물리·월드·센서 전송·`selectTarget` 규칙·조준 허용 각도(좌우 70°, 상하 75/35°)·보정 원뿔 반각 12°. 새 패키지 추가 없음.
- **확인함:** 타입 검사, 단위 테스트 14개 파일 99개 통과(신규 7개: 손목 장착 자세를 시뮬레이션한 조준 6개, `onFireMiss` 1개). 조준 테스트는 폰의 실제 변환 함수(`orientationToQuaternion`)로 자세를 만들어 팔 오른쪽 30°→yaw +30°, 왼쪽 30°→yaw −30°, 손목 위 20°→pitch +20°, 손목 롤 40°→조준 불변, 셋이 섞인 경우까지 고정했다. Rapier 월드를 직접 띄워 시작 지점(0,18,0)에서 물리 step 1회 후 yaw ±5~40° 범위에서 19~69m 표적이 잡히는 것도 확인했다. 빌드와 브라우저 테스트(Playwright Chromium 15개 중 14개 통과)도 돌렸다. 실패한 1개(`flow.spec.ts`의 호스트 오프라인 감지, 45초 대기)는 단독 재실행에서 통과했고 조준·연출 경로와 무관한 기존 타이밍 취약 테스트다. 마우스 모드의 부착·거미줄 표시 테스트는 통과했다.
- **확인 안 함:** 실기기 폰 조준. 센서가 없어 자동 검증으로는 대체할 수 없다. 특히 **장착 방향이 문서 기준(폰 상단이 손가락 쪽)과 다르면 좌우·상하가 반대로 움직인다.** 그때는 `client/host/aim.ts`의 `DEVICE_AIM_AXIS`를 `[0, -1, 0]`으로 바꾼다. 빗나감 연출의 체감 길이(260ms)와 실패음도 측정값이 아닌 제안 초기값이다.
- **기존 버그 아님(확인함):** 표적 선택·물리·월드 자체는 정상이다. Rapier는 콜라이더를 추가한 뒤 `step()`을 한 번 거쳐야 raycast가 새 콜라이더를 본다. 플레이 중에는 매 프레임 step이 돌아 문제가 없다.

## 연출 상태·오디오 오류 수정(2026-09-13)

- 음소거와 바람 재생 요청을 구분했다. 플레이 중 음소거를 해제하면 바람을 다시 만들고, 정지 상태에서 해제하면 재생하지 않는다.
- 오디오 노드 생성·재생 실패를 `SfxPlayer` 안에서 처리한다. 부분 생성된 노드를 포함해 정리하고 오디오를 비활성화해 게임 상태 전이·물리 콜백이 계속 실행되도록 했다. 음원 자연 종료와 명시적 정지 모두 연결을 해제하며 반복 정리도 가능하다.
- `setPhase`에서 플레이 외 단계의 음원·발사선·부착 플래시 정리를 통합했다. 폰 교체에도 같은 정리가 적용되고, 프레임 루프가 정지 중 발사선을 다시 표시하지 않는다. 일시정지 중 부착 물리 보존은 유지한다.
- 플래시 시간(220ms)과 발사선 맥동 계수(0.05/ms)는 `shared/config.ts`로 옮겼다. 값과 물리·센서 설정은 바꾸지 않았다.
- **확인함:** 오디오 회귀 단위 테스트 5개는 수정 전 실패·수정 후 통과했다. 로컬 Windows·Playwright Chromium에서 발사 중 정지와 재발사, 부착 상태 정지, 오디오 오류 주입 후 부착·종료·재시작, 실제 AudioContext의 음소거 복구, 모의 폰 입력의 플레이 중 폰 교체를 검증했다. 시각 효과는 브라우저 렌더 객체의 표시 상태로, 음원은 생성·연결 해제 상태로 확인했다. 테스트 응답에만 읽기 전용 관찰 함수를 넣었으며 제품 코드에는 테스트 훅을 추가하지 않았다.
- **확인 안 함:** 실제 폰·외부 모니터·핫스팟, 사람이 듣는 음질과 정지 순간의 청감, 20분 메모리 추이. 자동 검증으로 청감이나 장시간 누수 여부를 보장하지 않는다.
- **이번 자동 검증:** 타입 검사, 단위 테스트 14개 파일·95개, 브라우저 테스트 15개, 빌드, 변경 코드 Prettier 검사가 통과했다. 기존 Rapier 포함 번들의 크기 경고는 남아 있다.

## 밝은 한국풍 거리·거미줄 효과음·안내 화면(2026-09-13)

- **밝은 한국풍 거리(GM-02):** `client/host/scene.ts`가 하늘·조명을 밝게 바꾸고, 건물에 파스텔 팔레트(5색)와 창문 격자 텍스처, 도로에 차선(중앙 노란 점선·양쪽 흰 실선) 텍스처를 입혔다. 건물 위치로 정하는 결정적 해시로 색과 간판 유무·문구(한글 상점명 8종 중 1개, `hash % 3 === 0`인 건물만)를 고른다. 같은 위치는 재생성해도 항상 같은 장식을 받는다(`tests/unit/scene.test.ts`로 확인). 창문·차선·간판 텍스처는 모듈 상수로 한 번만 만들어 게임 내내 공유하고 폐기하지 않으며, 간판 지오메트리만 건물마다 만들어 구간 회수 시 함께 폐기한다(`createChunkMeshes`의 기존 geometry 폐기 경로를 그대로 탄다). 물리 콜라이더(`physics.ts`)와 부착 후보(`world.ts`)는 전혀 건드리지 않아 충돌·조준 판정에 영향이 없다. **세종대학교 등 학교 상징 건물은 포함하지 않았다.** 신뢰할 수 있는 공개 자료로 외관(형태·색·지붕 등)을 확인하지 못해(검색 결과에 텍스트 설명만 있고 사진을 직접 볼 수 없었다) AGENTS.md 지침에 따라 보류했다.
- **거미줄·표적 가독성:** 거미줄 색을 밝은 배경에서도 대비되는 진한 빨강(`0xd7263d`)으로 바꾸고, 조준점·표적 마커 테두리에 어두운 외곽선(`box-shadow`)을 더했다.
- **발사·부착 시각 효과:** `WebSwing`(`web.ts`)에 `onFireStart` 콜백과 `pendingTargetPoint`를 추가해 idle→firing 전이 순간에만 한 번 호출되게 했다(재발사 방지 로직은 기존 상태기계 그대로 재사용). `main.ts`가 firing 중에는 노란 점멸선(`fireBeamLine`)을, 부착 순간에는 확대되며 사라지는 원형 플래시(`attachFlash`)를 표시한다. 둘 다 실제 상태 전이에서만 트리거되며 타이머로 자동 종료되어 중복 표시가 없다. 카메라 위치·회전·FOV·시야각은 바꾸지 않았다.
- **최소 효과음:** `client/host/audio.ts`의 `SfxPlayer`가 새 패키지 없이 Web Audio 오실레이터로 발사·부착·해제 효과음을 합성한다. `AudioContext`는 `정면 보정`·`게임 시작`·`다시 하기`·음소거 버튼 클릭과(마우스 모드에서) 캔버스 클릭 안에서 `resume()`한다. 오디오 API가 없거나 생성에 실패해도 예외를 던지지 않고 게임은 그대로 진행된다(`available` 게터로만 확인). 정지·종료 시 `stopWind()`를 호출해 진행 중이던 바람 소리가 남지 않게 했다. 여유 항목이던 속도 기반 바람 소리(저음 톱니파+로우패스, 속도에 따라 음량·주파수 변화)도 함께 넣었다.
- **행사 안내 화면:** `client/index.html`의 `검증 시작`/`검증 중지`를 `게임 시작`/`정지`로 바꾸고, 단계별(연결·보정·시작 대기·플레이) 다음 행동을 안내하는 `#guide-section`을 추가했다(`paused`·`gameOver`는 기존 recovery/gameover 안내를 그대로 쓰므로 숨긴다). 상태·진단 정보는 `<details>`로 접어 기본은 닫혀 있고, 기존 운영자 버튼(보정·시작·정지·폰 교체·재시작)은 그대로 유지했다.
- **검증:** `npm run typecheck`, `npm run test:unit`(13개 파일 90개 테스트, 신규 5개: `web.test.ts`의 `onFireStart`/`pendingTargetPoint` 2개, `scene.test.ts`의 건물 색 결정성 1개는 기존 테스트에 추가), `npm run test:e2e`(11개 통과, 무변경) 통과를 확인했다. `npm run build` 통과(번들 크기 경고는 Rapier WASM 때문이며 기존과 동일). 로컬 Chromium(1280×720, 마우스 입력)에서 하늘·건물 색상·창문·차선이 렌더링되는 것, 안내 문구가 단계마다 바뀌는 것, 진단 정보가 기본적으로 접혀 있는 것, 음소거 버튼 클릭 시 라벨이 바뀌는 것, `pageerror`·콘솔 오류가 없는 것을 스크린샷과 함께 확인했다. 발사·부착 효과음과 시각 효과의 코드 경로는 단위 테스트(콜백 호출 시점·횟수)로 확인했으나, 실제 발사→부착 순간의 화면 렌더링을 스크린샷으로는 명확히 포착하지 못했다(거미줄이 카메라와 같은 위치에서 시작해 원근상 가늘게 보이는 기존 한계와 겹친다).
- **확인 안 함:** 실제 스피커·이어폰으로 효과음이 들리는지, 초보자가 새 안내 문구·시각 효과를 실제로 도움이 된다고 느끼는지, 실기기 폰 플레이. 세종대 건물은 신뢰할 수 있는 사진으로 재확인되면 후속으로 추가한다.

## 무한 도로·점수·정체 종료 구현(2026-09-13)

- **무한 도로(GM-01):** `client/host/world.ts`의 `createPracticeWorld`를 `ChunkedWorld`로 교체했다. 길이 60m 구간을 단위로 현재 구간 앞 4개·뒤 2개를 유지하고, 벗어난 구간의 mesh(`scene.ts`의 `createChunkMeshes`)와 콜라이더(`physics.ts`의 `addChunk`/`removeChunk`)를 함께 제거한다. **부착 중인 앵커가 속한 구간은 회수하지 않는다.** 배치는 구간 index로 seed를 만드는 내부 `mulberry32`로 정해져 생성 순서와 무관하게 재현된다(새 패키지 없음). 구간 0만 시작 직후 양쪽에 걸 수 있는 표적을 고정 배치한다.
- **점수·정체(GM-03, GM-04):** `client/host/progress.ts`를 새로 만들었다. 물리 step에서만 시간을 더하므로 정지·연결 중단 중에는 점수와 정체 타이머가 멈춘다. 한 step 안에서 전방 최고 도달 거리를 먼저 갱신한 뒤 정체를 판정하고, 기준점보다 5m 늘면 타이머를 초기화한다. 뒤로 갔다 돌아오는 왕복은 최고값을 갱신하지 않으므로 초기화되지 않는다. 5초 경고, 8초 종료, 점수는 `floor(진행 시간 × 10)`이다.
- **HUD(GM-05):** 캔버스 위에 점수·속도·정체 경고를 표시하고, 종료 화면에 종료 이유와 최종 점수를 남긴다.
- **재시작(GM-07):** 새 게임과 재시작은 위치·월드 구간·점수·정체 타이머를 함께 초기화한다(`resetRun`). 중단 게임 재개 경로에서는 초기화하지 않는다.
- 수치는 PRD 5절·ARCHITECTURE 5절의 제안 초기값을 그대로 `shared/config.ts`의 `world`/`progress`에 넣었다. 측정값이 아니며 플레이 후 조정 대상이다.
- **1,000m 좌표 재기준화는 구현하지 않았다.** 부착 중인 joint·앵커·보간 상태를 한 프레임에 함께 옮겨야 해 스윙 중 위험이 크고, 이 게임 길이(수 분, 초기 속도 14m/s 기준 10km까지 12분 이상)에서는 좌표 정밀도가 문제가 되지 않는다고 판단했다. `main.ts`에 근거와 함께 TODO를 남겼다. **장시간 실행으로 실제 측정한 결과는 아니다.**
- **확인함:** 500m 전진 시뮬레이션에서 앞 구간의 부착 후보와 도로가 계속 존재하고 활성 구간·scene 객체 수가 7개를 넘지 않는 것을 실제 Rapier·Three.js로 확인했다(`tests/unit/worldStreaming.test.ts`). 로컬 Chromium(1280×720, 마우스 입력)에서 건물에 매달린 채 유지하면 6~7초에 정체 경고가 뜨고 약 9.7초에 `전진 정체로 종료되었습니다`로 끝나는 것, 그동안 점수가 0.1초당 1점으로 오르는 것, `pageerror`·콘솔 오류가 없는 것을 관찰했다.
- **확인 안 함:** 실기기 폰 플레이, 60fps 실측, 20분 연속 실행과 메모리 추이, 초보자 체감. 마우스로 장거리 연속 스윙을 이어가는 실제 플레이 감각은 검증하지 않았다(스크립트 조작으로는 몇 초 만에 추락했다. 사람이 조작할 때도 어려운지는 확인하지 못했다).

## 저장소 재점검과 수정(2026-09-13)

- **다른 QR 접속 시 이전 세션으로 복구되는 문제:** 같은 탭에서 다른 호스트의 초대 URL을 열어도 저장된 컨트롤러 토큰으로 이전 호스트에 연결됐다. 컨트롤러가 복구 요청에 현재 `inviteToken`을 포함하고, 서버는 대상이 다르면 복구를 거절한다. 이후 기존 참여 경로로 새 호스트에 연결한다. 같은 초대의 새로고침·재접속과 토큰만 보내는 기존 복구 요청은 유지한다.
- **이동한 거미줄의 표시 경계 누락:** 줄 정점을 갱신해도 Three.js의 경계 구체가 이전 위치에 남아 화면 안의 줄을 화면 밖으로 판정할 수 있었다. `updateRopeLine`에서 정점과 경계를 함께 갱신한다.
- **물리 자원 해제 누락:** `PhysicsWorld.dispose()`에서 월드와 별도로 할당한 Rapier 이벤트 큐도 해제한다. 설치된 Rapier 타입 문서의 수동 해제 요구를 확인했다. 게임 재시작은 월드를 재생성하지 않으므로, 이를 매 재시작마다 발생하는 누수로 보지는 않는다.
- 앞의 두 오류는 각각 Playwright와 Three.js 프러스텀 판정 단위 테스트로 수정 전 실패·수정 후 통과를 확인했다. 이벤트 큐 해제는 기존 실제 Rapier 단위 테스트의 생성·실행·정리 경로로 확인했다. 실제 폰과 장시간 메모리 측정은 수행하지 않았다.
- 기존 입력·물리·거미줄 모듈 분리를 유지했다. 추가 기능 없이 고칠 수 있는 연결·렌더링·자원 정리에 범위를 제한했으며, 패키지나 물리·센서 튜닝값은 바꾸지 않았다.

## 조준 표시와 연결 복구 완성(2026-09-13)

- **캔버스·패널 비중첩:** 운영자 패널(320px)이 캔버스 오른쪽을 가리던 문제를 `#game-area`/`#panel`을 나란히 배치하는 flex 레이아웃으로 해결했다. `scene.ts`의 캔버스 크기·카메라 종횡비는 `window.innerWidth/innerHeight`가 아니라 `#game-area` 컨테이너 크기를 기준으로 계산한다.
- **조준·표적 표시를 실제 발사 방향과 일치:** 폰 조준점이 쓰던 `anglesToScreenRatio`(각도 선형 매핑, 화면 종횡비 미반영)를 제거하고, `aim.ts`의 `directionToScreenRatio`가 실제 발사에 쓰는 3D 방향을 카메라 원근 투영으로 화면 비율로 변환한다. 마우스·폰 조준점 모두 이 함수 하나로 표시하므로 표시와 발사가 항상 같은 계산을 쓴다. 마우스 조준점도 이제 포인터 위치를 따라 이동한다.
- **표적 미리보기 마커 추가:** `main.ts`가 매 프레임 `web.ts`의 `selectTarget`(발사 시 쓰는 것과 동일한 함수·후보·설정)로 부착 예정점을 미리 계산해 `#target-marker`로 별도 표시한다. `playing` 단계의 `idle` 상태에서만 계산하며, 화면 밖이면 숨긴다. 조준점도 화면 밖일 때 마름모 모양으로 바뀐다(`data-onscreen`).
- **재개 보존 버그 수정:** `goToPaused`가 `pendingResume = phase === 'playing'`으로 덮어써, 재보정까지 마친 `ready` 상태에서 다시 입력이 끊기면 재개 대기가 꺼지고 다음 시작이 새 게임처럼 위치·속도를 초기화했다. `resumeState.ts`의 `nextPendingResume`(기존 값이 true면 유지)으로 분리해 고쳤다.
- 새 패키지 추가나 물리·센서 튜닝값 변경은 없다. `directionToScreenRatio`는 단위 테스트로 여러 종횡비에서 `mouseNdcToDirection`의 역함수임을 확인했고, `nextPendingResume`은 문서화된 버그 시나리오를 그대로 재현하는 단위 테스트로 고정했다. 마우스 조준점 이동과 표적 마커 표시는 Playwright로 확인했다.
- **확인 안 함:** 재개 보존 수정은 단위 테스트로만 검증했다. 폰 연결에서 소켓은 유지된 채 입력 프레임만 끊기는 상황(문서화된 버그의 실제 트리거)을 Playwright로 재현하려면 컨트롤러 쪽에 테스트 전용 훅이 필요해 이번에는 추가하지 않았다. 실기기에서의 반복 재연결·재개도 아직 확인하지 못했다.

## 추가 코드 점검과 수정(2026-09-13)

- **상태 중계 검증 누락 수정:** `host:state`에 `null`, 잘못된 단계·보정 타입·정지 사유를 보내면 그대로 폰에 전달되었다. 폰은 `state.phase`를 직접 읽으므로 `null`은 클라이언트 오류를 유발할 수 있었다. 서버가 잘못된 상태를 거절하도록 수정했다. 기존 컨트롤러 상태 검증도 `shared/stateValidation.ts`의 순수 함수로 분리했다.
- **활성 소켓 복구 수정:** 복구 토큰으로 새 소켓을 등록해도 이전 소켓이 살아 있었고, 컨트롤러 연결 교체를 호스트에 알리지 않았다. 이전 연결을 먼저 종료·통지한 후 복구하도록 바꿨다. 호스트가 기존 순번·자세·보정을 초기화하는 경로를 거치며, 이전 호스트 소켓도 복구 시 종료한다.
- **마우스 중지 후 재개 수정:** `paused`에서 보정 버튼과 시작 버튼이 모두 비활성화되어 재개할 수 없었다. 마우스 모드는 시작 버튼으로 재개하고, 폰 모드는 기존 재보정 절차를 유지한다. 버튼과 실제 실행의 시작 조건을 `canStartPlaying`으로 통일했다. 마우스 모드를 복구 불가능한 `pairing` 상태로 보내던 폰 교체 버튼도 비활성화했다.
- 위 세 문제는 수정 전 실패하는 Playwright 테스트로 재현한 뒤 수정했다. 상태 검증 단위 테스트 17개와 활성 소켓 복구·마우스 재개 통합 테스트를 추가했다. 패키지 추가나 물리·센서 튜닝값 변경은 없다.
- 별도 로컬 Chromium 실행(1280×720, 마우스 입력)에서 발사·운영자 중지·재개를 조작하고 중지 화면의 시작 버튼 활성화, 재개 후 `playing`, 브라우저 `pageerror` 없음도 확인했다. 사람의 체감 플레이나 폰 실기기 검증은 아니다.

## 남은 확인 및 개선 후보

- 실제 iPhone Safari·Android Chrome에서 장착 방향과 조준 좌우·상하 부호, 화면 회전 보정, 두 손가락 조작 확인이 필요하다. 모의 센서·마우스 테스트로 호환성을 보장하지 않는다.
- 폰 입력 경로는 `anglesToDirection`으로 동일한 `selectTarget`·물리 파이프라인, 그리고 조준점·표적 마커 표시(`directionToScreenRatio`)까지 공유한다. 좌우·상하 부호는 손목 장착 자세를 시뮬레이션한 단위 테스트로 고정했으나(위 [폰 조준 좌우 회전 수정과 빗나감 연출](#폰-조준-좌우-회전-수정과-빗나감-연출2026-09-13)), 실제 폰 자세로 부착 판정과 화면 표시가 기대대로 맞는지는 아직 확인하지 않았다.
- 소켓은 유지된 채 입력 프레임만 끊기는 상황에서 `ready` 상태의 재개 보존이 실제로 동작하는지는 단위 테스트로만 확인했다([조준 표시와 연결 복구 완성](#조준-표시와-연결-복구-완성2026-09-13) 참고). Playwright·실기기 재현은 아직이다.
- 세션 ACK 응답 제한 시간과 저장소 접근 실패 안내는 아직 없다. 연결 불가·브라우저 저장 차단 환경의 안내 개선 후보이다.
- 입력 전송 빈도와 센서 유효 시간 등 진단 화면의 설정·주기 정리가 필요하다. 측정 전 빈도나 장착 좌표계를 임의로 확정하지 않았다.
- `client/host/main.ts`에는 게임 상태 전이·HUD 갱신·프레임 루프가 함께 있다. 무한 도로·점수를 추가하며 더 커졌으므로 상태 전이 분리가 리팩토링 후보다. 이번에도 회귀 추적을 위해 기능 추가와 구조 변경을 섞지 않았다.
- 정체 종료는 실기기가 아닌 마우스 입력에서만 관찰했다. 정체 수치(5m·5초·8초)와 점수 배율은 측정이 아닌 제안 초기값이라 실제 플레이 후 조정이 필요하다.
- 1,000m 좌표 재기준화 미구현. 장시간 실행에서 좌표 정밀도 문제가 관측되면 구현한다.
- 실제 핫스팟 지연, 20분 연속 실행, 10회 게임 재시작, 초보자 체감 테스트는 수행하지 않았다.
- 닉네임 로컬 기록(GM-06)은 이번 범위에서 제외했다(계획 문서 기준). 한국풍 표현(GM-02)과 발사·부착·해제 효과음·바람 소리는 위 [밝은 한국풍 거리·거미줄 효과음·안내 화면](#밝은-한국풍-거리거미줄-효과음안내-화면2026-09-13)에서 구현했다. 세종대학교 등 학교 상징 건물은 신뢰할 수 있는 외관 사진을 확인하지 못해 보류했다.

## 이전 자동 검증 결과 — 무한 도로 구현 시점

Windows 작업 환경, Node.js v24.19.0, 로컬 서버와 Playwright 기본 Chromium·모의 센서·마우스 입력 기준이다. 실제 폰·외부 모니터·핫스팟 성능 측정은 포함하지 않는다.

- `npm.cmd run typecheck`: 통과.
- `npm.cmd run test:unit`: 13개 파일, 87개 테스트 통과. 구간 생성·회수(`world`), 점수·정체(`progress`), 500m 스트리밍(`worldStreaming`), 구간 콜라이더 회수(`physics`), 구간 mesh 회수(`scene`) 테스트를 추가했다.
- `npm.cmd run test:e2e`: 총 11개 통과. 점수 증가·종료 후 고정·재시작 초기화 테스트를 추가했다. 정체 종료는 8초 매달림이 필요해 e2e에 넣지 않고 단위 테스트와 수동 브라우저 관찰로 확인했다. 낙하 지연 테스트가 거미줄 선의 실제 화면 표시까지 보장하지는 않는다.
- `npm.cmd run build`: 최종 변경 기준 통과. Rapier WASM 포함으로 `host` 번들이 약 3.3MB(gzip 1.2MB)로 커졌다. 코드 스플리팅은 이번 범위에서 하지 않았다.

이번 재점검은 로컬 작업 환경에서 실행했다. 브라우저의 오프라인 전환 후 Socket.IO 연결 종료 감지는 입력 중단 감지보다 늦을 수 있어, 테스트는 입력 정지와 실제 재접속을 별도로 기다린다.
