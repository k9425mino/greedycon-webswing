# 구현 현황과 코드 점검

2026-09-13 갱신. PRD와 Architecture는 전체 게임의 목표 설계이며, 무한 도로·점수·정체 종료·한국풍 그래픽·소리는 아직 후속 범위다.

## 구현된 범위

| 영역 | 구현 |
|---|---|
| 서버 | Express 개발/정적 서버, Socket.IO 중계, QR 초대, 역할별 복구 토큰, 폰 교체, 빈 세션 정리 |
| 폰 | 센서 권한 요청, 방향 쿼터니언 변환, 화면 방향 반영, 다중 포인터 터치, 화면 숨김 상태 전달 |
| 호스트 | QR, 정면 보정, 상대 회전 조준점, 누름 표시, 입력 중단 감지, 운영자 시작·중지, 수신 빈도 표시 |
| 물리 | `@dimforge/rapier3d-compat` 0.20, 회전 고정 구체 플레이어(CCD), 고정 60Hz accumulator + 보간 렌더링, 바닥 접촉 종료 |
| 월드 | 고정 연습 구간(상자 건물 3쌍, 도로), 무한 생성·회수는 미구현 |
| 조준·거미줄 | 직접 raycast 우선 + 보정 원뿔 후보 선택(공용 `selectTarget`), `idle/firing/attached/releasedRequired` 상태기계, 부착 시 1회 보조 당김, 해제 시 속도 보존 |
| 마우스 입력 | `?input=mouse`에서만 활성화, 캔버스 좌표 → 원근 투영 방향, 왼쪽 버튼 유지. 폰 입력 경로(연결·보정 요구)는 그대로 유지 |
| 정지·재개·재시작 | 일시정지 중 물리·부착 보존, 재개 직전 줄 해제와 재발사 요구, 새 게임만 초기 전방 속도 부여, 재시작 버튼으로 위치·속도·줄 초기화 |
| 화면 | Three.js 전방 카메라, 건물·플레이어·거미줄 렌더링, 렌더 루프 단일화(물리 루프에 통합) |
| 입력 빈도 | 비교용 30/60/120Hz 선택, 기본 60Hz. 명세의 최대 30Hz와 차이가 있으며 실제 성능 측정 결과는 아님 |

## 이번 점검(2026-09-13)에서 확인한 것과 못 한 것

- 확인함: 마우스 입력으로 `npm run dev` 실행 후 브라우저(Playwright Chromium)에서 새 게임 시작 → 조준 없이 추락 → 재시작, 그리고 건물을 겨눠 부착 후 낙하가 지연되는 것을 실제로 관찰했다(`tests/e2e/mouseSwing.spec.ts`).
- 확인함: 물리 규칙 일부는 실제 Rapier 월드로 검증했다 — 바닥 접촉 감지, 느슨한 줄의 비압축(자유낙하 속도 유지), 해제 시 속도 보존(`tests/unit/physics.test.ts`).
- 확인 안 함: 실제 iPhone/Android 손목 장착, 폰 조준으로 실제 표적 부착, 정체·점수(이번 범위에서 미구현), 20분 연속 실행·10회 재시작·초보자 체감 테스트, 60fps 실측.
- 알려진 제약: 호스트 화면의 운영자 패널(우측 320px)이 캔버스 오른쪽 일부를 가려 마우스로 그 영역을 조준할 수 없다. 폰 입력에는 영향 없음(별도 기기 화면). 실기기 검증 전까지는 개발 편의상 남겨둔다.

## 이전 점검(2026-09-12)의 수정

- `/controller` 리다이렉트에서 초대 쿼리 보존.
- Socket.IO 재접속 시 세션 재등록, 호스트 연결 중단 통지, 연결이 없는 동안 상태/교체 명령 큐 적재 방지.
- 재연결 시 호스트 순번·자세·누름·센서 상태 초기화. 새 유효 입력과 센서 준비, 터치 해제 확인 후 보정·시작 허용.
- 준비 상태에서도 입력 중단·화면 숨김·센서 상실 시 재보정 요구. 준비 조건에 맞춰 버튼 활성화.
- 폰 연결이 끊겨도 운영자의 교체 전까지 기존 복구 토큰 유지.
- 서버 중계 시 현재 역할별 소켓 확인, 중복 세션 등록 차단, ACK 없는 등록 요청 무시, 입력·컨트롤러 상태 검증.
- 센서 API 부재 및 유한하지 않은 센서 값 처리, 시작 버튼 중복 실행 방지.
- 입력 순번의 안전한 정수 검사와 극단적인 유한 쿼터니언의 정규화 처리.

## 남은 확인 및 개선 후보

- 실제 iPhone Safari·Android Chrome에서 장착 방향과 조준 좌우·상하 부호, 화면 회전 보정, 두 손가락 조작 확인이 필요하다. 모의 센서·마우스 테스트로 호환성을 보장하지 않는다.
- 폰 입력 경로는 `anglesToDirection`으로 동일한 `selectTarget`·물리 파이프라인에 연결했지만, 실제 폰 자세로 부착이 되는지는 확인하지 않았다.
- 운영자 패널이 캔버스 우측을 가리는 문제(위 표 참고)를 실기기 검증 전에 정리할지 결정이 필요하다.
- 세션 ACK 응답 제한 시간과 저장소 접근 실패 안내는 아직 없다. 연결 불가·브라우저 저장 차단 환경의 안내 개선 후보이다.
- 입력 전송 빈도와 센서 유효 시간 등 진단 화면의 설정·주기 정리가 필요하다. 측정 전 빈도나 장착 좌표계를 임의로 확정하지 않았다.
- 실제 핫스팟 지연, 20분 연속 실행, 10회 게임 재시작, 초보자 체감 테스트는 수행하지 않았다.
- 무한 도로 생성·회수, 점수, 정체 종료, 한국풍 표현, 로컬 기록은 이번 범위에서 제외했다(계획 문서 기준).

## 자동 검증 결과

Windows 작업 환경, Node.js v24.19.0, 로컬 서버와 Playwright 기본 Chromium·모의 센서·마우스 입력 기준이다. 실제 폰·외부 모니터·핫스팟 성능 측정은 포함하지 않는다.

- `npm.cmd run typecheck`: 통과.
- `npm.cmd run test:unit`: 7개 파일, 47개 테스트 통과(신규: `web.test.ts` 거미줄 상태기계, `physics.test.ts` 실제 Rapier 월드 기반 바닥 접촉·느슨한 줄·해제 속도 보존).
- `npm.cmd run test:e2e`: 기존 4개(연결·재보정·재접속, 초대 쿼리 유지, 센서 권한 거부, 서버 중계 검증)에 더해 신규 `tests/e2e/mouseSwing.spec.ts` 2개(마우스 새 게임·추락·재시작, 건물 부착으로 낙하 지연) 포함 총 6개 통과.
- `npm.cmd run build`: 최종 변경 기준 통과. Rapier WASM 포함으로 `host` 번들이 약 3.3MB(gzip 1.2MB)로 커졌다. 코드 스플리팅은 이번 범위에서 하지 않았다.

Vitest/Vite는 샌드박스의 상위 폴더 접근 제한으로 최초 실행이 실패했으며, 실행 권한을 확장한 뒤 위 검증을 수행했다. 브라우저의 오프라인 전환 후 Socket.IO 연결 종료 감지는 입력 중단 감지보다 늦을 수 있어, 테스트는 입력 정지와 실제 재접속을 별도로 기다린다.
