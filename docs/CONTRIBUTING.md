# 기여 가이드

손목 웹슈터 웹스윙 게임 부스 프로젝트의 협업 규칙이다. 행사일은 2026-09-17, 기능 동결 목표는 2026-09-16 오전이다. 현재 개발자는 1명이며 행사 전 팀원이 합류할 수 있다. 짧은 기간에 맞춰 절차는 최소로 둔다.

먼저 읽을 문서: [PRD.md](PRD.md) (무엇을 만드는가), [ARCHITECTURE.md](ARCHITECTURE.md) (어떻게 만드는가).

## 1. 로컬 실행

Windows에서는 `npm.cmd`를 쓴다(예: `npm.cmd run dev`). 아래는 실제로 실행해 확인한 명령이다(Node.js v24.19.0, Windows 11).

```bash
npm install
npm run dev
```

- 노트북 게임: `http://localhost:5173/`
- 스마트폰 컨트롤러: `http://localhost:5173/controller` (QR로 접속, `/controller`는 `/controller/`로 자동 리다이렉트)

빌드 후 정적 파일로 실행하려면:

```bash
npm run build
npm run start
```

`npm run typecheck`, `npm run test:unit`(Vitest), `npm run test:e2e`(Playwright)로 검증한다. `npm run format`은 `client/`, `server/`, `shared/`, `tests/`, 설정 파일에만 적용된다(`docs/`, 루트 `*.md`는 `.prettierignore`로 제외).

스마트폰 방향 센서는 HTTPS에서만 동작한다. 로컬 개발에서 폰으로 접속하려면 cloudflared 임시 터널을 쓴다.

1. cloudflared를 설치한다(Windows: `winget install --id Cloudflare.cloudflared`).
2. `npm run dev`로 서버를 띄운 채 별도 터미널에서 `npm run tunnel`을 실행한다.
3. 출력된 `https://<임의문자열>.trycloudflare.com` 주소를 **노트북 브라우저에서도** 열어 그 주소로 접속한다. QR은 접속한 origin을 그대로 사용하므로, localhost로 열면 QR도 localhost를 가리켜 폰에서 접속할 수 없다.
4. 터널 주소는 매번 새로 발급되는 임시 URL이라 재실행할 때마다 바뀐다. 행사 운영용 배포는 후속으로 결정한다.

확인 조건: Node.js v24.19.0, Windows 11, cloudflared 2026.9.1(quick tunnel)으로 `npm run dev` + `npm run tunnel` 조합의 HTTPS 접속과 `npm run build`/`npm run start`를 확인했다. 실제 iPhone·Android 접속은 아직 실기기로 확인하지 않았다.

## 2. 브랜치와 커밋

- `main`에 직접 푸시한다. PR과 승인 대기는 두지 않는다.
- **`main`은 항상 실행 가능해야 한다.** 깨뜨렸다면 고치거나 즉시 되돌린다. 남을 기다리게 하지 않는다.
- 실험적이거나 반나절 이상 걸리는 작업은 브랜치를 파고, 돌아가는 상태가 되면 `main`에 머지한다.
- 커밋 메시지는 `영역: 내용` 형식으로 쓴다. 앞의 영역 태그는 영어 소문자, 뒤의 내용은 한국어 한 줄로 무엇을 왜 바꿨는지 적는다.
- 영역 태그는 `input`, `physics`, `world`, `hud`, `server`, `docs`, `chore`를 쓴다. 맞는 게 없으면 새로 만들되 영어 한 단어로 한다.

```
input: 포인터 두 개 중 하나만 떼도 줄 유지
physics: 부착 시 임펄스가 매 프레임 적용되던 문제 수정
docs: 일정을 4일 기준으로 축소
```

- 커밋은 작게 나눈다. 무관한 변경을 한 커밋에 섞지 않는다.

## 3. 여럿이 함께 작업할 때

팀원이 합류하면 다음만 지킨다.

- 작업 시작 전에 **어느 영역을 맡는지 먼저 말한다.** 영역은 입력·중계, 물리·거미줄, 월드·렌더링, HUD·기록으로 나눈다. 같은 파일을 둘이 동시에 고치지 않는 것이 목적이다.
- 작업 시작 전에 `git pull --rebase`, 끝나면 바로 푸시한다. 로컬에 하루치 커밋을 쌓아두지 않는다.
- 공유 타입(`InputFrame`, `AimInput`, `HostState`)과 게임 설정값을 바꿀 때는 **바꾸기 전에** 알린다. 다른 영역이 같이 깨진다.

## 4. 코드 규칙

- 포맷은 Prettier가 결정한다. 저장 시 자동 정렬을 켜두고, 들여쓰기나 따옴표를 두고 논의하지 않는다.
- 식별자(변수·함수·타입·파일)는 영어로 쓴다. 설명 주석은 한국어로 쓴다.
- 주석은 코드가 무엇을 하는지가 아니라 왜 그렇게 했는지를 적는다. 특히 실기기 테스트로 정한 부호나 값에는 근거를 남긴다.
- TypeScript를 쓰고 `any`는 피한다. 특히 네트워크로 들어온 값은 신뢰하지 않고 타입·유한값·순번을 검사한다.
- **튜닝 가능한 수치는 코드에 흩어놓지 않는다.** 점수, 정체 시간, 중력, 속도, 조준 각도, 전송 주기 등은 모두 하나의 게임 설정 모듈에 모은다. 플레이 테스트 중 값만 고쳐 재시도할 수 있어야 한다.
- 게임 규칙(점수, 정체 판정, 거미줄 상태 전이)은 렌더링과 분리해 테스트 가능한 순수 함수로 둔다.
- 지금 필요하지 않은 추상화와 범용 프레임워크는 만들지 않는다. 부스 하루를 위한 코드다.
- 기존 코드 스타일을 따른다. 관련 없는 코드를 정리하지 않는다.

## 5. 검증

- 게임 규칙과 상태 전이는 Vitest로 테스트한다. 브라우저 흐름은 Playwright를 쓴다.
- 물리와 조준은 자동 테스트로 충분하지 않다. **직접 플레이해서 확인한 뒤 푸시한다.**
- 모의 센서 입력이 통과했다고 실기기에서 된다고 보지 않는다. 입력·센서·장착 관련 변경은 실제 iPhone과 Android에서 확인한다.
- 실기기·성능·지연을 측정하면 기종, OS, 브라우저, PC 사양, 네트워크와 함께 결과를 기록한다. 측정하지 않은 값을 문서에 목표가 아닌 사실로 적지 않는다.
